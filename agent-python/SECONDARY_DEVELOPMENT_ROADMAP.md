# VoiceAgentProject 二次开发路线

> 历史规划文档：当前语音助手 UI 统一由苍穹外卖用户端维护，Python 工程只提供 Agent 后端。
> 本文中的 `ui/` 路径和客服工作台设想均为旧方案，不是当前工程结构或已承诺功能。

> 目标岗位：Agent 应用开发工程师
> 项目定位：可写入简历、可现场演示、可经受技术面试追问的电商售后 Voice Agent
> 实施原则：基于现有项目增量开发，继续使用 JSON Mock 数据，不推倒重写，不机械增加中间件。

## 1. 路线结论

推荐采用以下五阶段路线：

1. 实时链路可靠性与会话一致性
2. 工单生命周期闭环
3. 工具可观测协议与可信 RAG 引用
4. 客服工作台
5. 指标评估、测试固化与简历交付

推荐顺序为：

```text
链路可靠性
  -> 工单业务闭环
  -> 结构化工具事件与 RAG 引用
  -> 客服工作台
  -> 指标、测试、演示和简历材料
```

这条路线优先展示 Agent 应用开发岗位真正关心的能力：异步流式编排、状态管理、工具副作用控制、RAG 可信性、前后端事件协议、可观测性和评估，而不是只展示模型 API 调用或页面效果。

预计总工时：**10-15 个个人开发日**。若外部模型 SDK 行为与当前假设不一致，额外预留 2-3 天排查时间。

## 2. 当前基线

### 已有且应复用

- FastAPI WebSocket 入口和每连接一个 `VoiceSession` 的隔离方式。
- Fun-ASR partial/final 识别适配器。
- Agent 文本增量输出和 Qwen TTS 增量输入。
- 单 WebSocket 发送协程和统一发送队列。
- Agent task、TTS 和前端播放队列的基础打断逻辑。
- 订单、物流、客户、工单创建、政策检索和联网搜索工具。
- LangGraph `InMemorySaver` 多轮上下文。
- Vue 3 麦克风采集、PCM 播放、字幕和对话展示。
- JSON Mock 数据、原子工单文件写入和基础工具单元测试。

### 当前关键缺口

- 历史日志出现工具调用消息序列不完整导致的 DeepSeek 400。
- 打断协议没有 `turn_id`，旧轮 TTS 事件可能污染新轮。
- 工单只能创建，不能查询、催办或查看历史。
- 工具调用过程不能传到前端。
- RAG 引用依赖解析模型回答文本，不是结构化事实。
- RAG 没有拒答阈值和可靠的索引更新策略。
- 缺少会话链路、WebSocket、RAG 和前端状态测试。
- 缺少可证明“低延迟”“成功率”的指标数据。

## 3. 范围取舍

### 本轮二开必须完成

- 流式链路稳定、可打断、会话隔离、异常可恢复。
- 工单创建、查询、催办和历史记录闭环。
- 工具调用和政策引用的结构化事件协议。
- 客户信息、工具轨迹和对话组成的客服工作台。
- 延迟、工具成功率和 RAG 指标的记录与导出。
- 关键模块自动化测试和一套稳定演示脚本。

### 暂不实施

- 真实电商、物流或 CRM 平台接入。
- Redis、Kafka、微服务、分布式向量数据库。
- 登录、权限、多租户和生产级数据合规体系。
- 长期记忆和跨设备会话恢复。
- 没有标注集支撑的 ASR 准确率或 RAG 准确率宣传。

## 4. Phase 1：实时链路可靠性与会话一致性

### 阶段目标

解决多轮对话、工具调用和用户打断之间的竞态，使语音链路成为后续业务与 UI 的可靠基础。

### 当前状态

**部分完成。** 已有 ASR partial/final、Agent/TTS 流式衔接、发送队列和基础打断；但没有轮次标识，且历史日志已出现不完整工具消息导致的 400。

### 开发任务与顺序

1. 定义会话和轮次模型：`session_id`、递增 `turn_id`、当前活动轮次和允许的状态转移。
2. 为 `stt.final`、Agent、TTS、播放控制、错误事件增加 `turn_id`。
3. 后端过滤已取消轮次的迟到 Agent/TTS 事件；前端只接收当前轮次的文本和音频。
4. 验证 LangGraph 在工具调用期间被取消时的 checkpoint 行为，避免残留不完整的 `tool_calls` 历史。
5. 明确取消策略：被打断轮次不进入后续对话历史，或以完整的取消结果收尾。
6. 正确识别 `websocket.disconnect`，关闭后停止接收和发送。
7. 为 LLM、工具、TTS 控制操作定义超时和错误分类。
8. 为发送队列增加容量或慢客户端策略，避免 PCM 无限积压。
9. 使用 Fake ASR、Agent、TTS 编写确定性状态机测试。

### 预计涉及文件

- 修改 `agent/events.py`：统一事件字段和轮次协议。
- 修改 `agent/session.py`：状态机、轮次过滤、打断、超时和背压。
- 修改 `agent/llm_agent.py`：取消和检查点一致性。
- 修改 `agent/main.py`：WebSocket 断线边界。
- 修改 `ui/src/composables/useVoiceAgent.js`：当前轮次状态管理。
- 修改 `ui/src/services/voiceSocket.js`：关闭和协议异常处理。
- 新增 `tests/test_session.py`、`tests/test_llm_agent.py`、`tests/fakes.py`。

### 前后端协作

- 保持同一条 WebSocket 承载 JSON 事件和 PCM 音频。
- JSON 事件统一携带 `session_id`、`turn_id` 和事件时间。
- 若二进制 PCM 无法自带轮次信息，后端必须在切换轮次前完成服务端隔离；必要时将音频改为带头部的二进制协议，但不作为首选。

### 验收标准

- 连续说两句话时，第一轮被取消，第二轮正常回答。
- TTS 播放中打断后立即静音，不再播放旧轮迟到音频。
- 工具调用中打断后继续提问，不出现 DeepSeek 工具消息序列 400。
- 重复 ASR final 不产生重复 Agent 轮次。
- 浏览器断开后，后台任务和模型连接能够释放。
- 两个并发会话的上下文、状态和音频互不串扰。

### 测试计划

- 单元测试：状态转移、重复 final、轮次过滤、超时分类。
- 集成测试：Fake Provider 驱动完整 `VoiceSession`。
- WebSocket 测试：正常关闭、异常断开、慢客户端。
- 手动测试：思考中打断、播放中打断、连续追问。

### 难点和风险

- LangGraph 取消时的 checkpoint 提交边界需要实测。
- Qwen TTS 是否提供响应 ID 将影响旧音频隔离方式。
- `response.audio.done` 和 `response.done` 可能导致重复 finished 事件。

### 预计工时

**2-3 天。** 最大不确定性是 LangGraph 和 Qwen TTS SDK 的取消语义。

### 阶段交付物

- 有明确状态图和轮次协议的实时会话链路。
- 不依赖外部模型的 Session 回归测试。
- 一份打断、断线和多会话验证记录。

## 5. Phase 2：工单生命周期闭环

### 阶段目标

将当前“只能创建”的工单升级为可查询、可催办、可审计的最小售后闭环。

### 当前状态

**部分完成。** `ticket_create` 已校验客户、订单归属和问题描述，并使用进程内锁及临时文件替换写入；查询、催办和历史记录尚未实现。

### 开发任务与顺序

1. 定义工单 schema：状态、优先级、创建/更新时间、催办次数和 `history`。
2. 设计旧数据兼容策略，读取没有 `history` 的记录时补默认值。
3. 实现 `ticket_lookup`：按工单号精确查找，或按客户 ID 返回最近工单。
4. 实现 `ticket_urge`：校验工单状态，调整优先级，记录催办历史。
5. 定义业务规则：已关闭工单不能催办；短时间重复催办不重复升级。
6. 为写操作增加 `operation_id` 或等效幂等键，防止模型重试造成重复副作用。
7. 将新工具注册到 Agent，并补充提示词规则。
8. 补齐正常、异常、重复执行和并发写测试。

### 预计涉及文件

- 建议新增 `agent/tools/ticket_service.py`，避免继续扩大 `customer_service.py`。
- 修改 `agent/tools/__init__.py`：导出新工具。
- 修改 `agent/llm_agent.py`：注册工具和完善提示词。
- 修改 `data/tickets.json`：采用增强后的示例 schema。
- 新增 `tests/test_ticket_tools.py`。

### 前后端协作

- 本阶段先让 Agent 可以用自然语言完成闭环。
- 工单结果应同时返回适合朗读的文本和可用于后续事件展示的结构化数据。
- 正式的工具调用 UI 在 Phase 3/4 接入。

### 验收标准

- 创建工单后可以立即按工单号查询。
- 按客户 ID 可以查询其最近工单列表。
- 首次催办提升优先级并追加历史记录。
- 短时间重复催办不会重复升级或重复追加相同操作。
- 已关闭或不存在的工单返回明确业务提示。
- Agent 不会因重试重复创建同一工单。

### 测试计划

- 单元测试：字段校验、状态规则、查询方式、历史追加、幂等。
- 文件测试：旧 schema 兼容、JSON 损坏、原子写入失败。
- 并发测试：同进程多个工单写操作不会相互覆盖。
- Agent 集成测试：创建后追问状态、再执行催办。

### 难点和风险

- JSON Mock 只承诺单进程演示可靠，不支持多进程强一致。
- 模型可能重复调用写工具，幂等不能只依赖提示词。

### 预计工时

**1.5-2.5 天。** 最大不确定性是幂等键如何从 Agent 调用上下文稳定传入。

### 阶段交付物

- `ticket_create`、`ticket_lookup`、`ticket_urge` 完整工具集。
- 可追溯的工单操作历史。
- 工单生命周期测试报告。

## 6. Phase 3：工具可观测协议与可信 RAG 引用

### 阶段目标

让工具调用和 RAG 来源成为结构化、可追踪的数据，而不是只能从模型回答文字中猜测。

### 当前状态

**部分完成。** 工具和向量检索已有代码，但 Agent 只输出自然语言；前端引用依赖正则，RAG 没有拒答阈值和索引版本策略。

### 开发任务与顺序

1. 定义 `tool.called`、`tool.finished`、`tool.failed` 事件 schema。
2. 每次调用生成 `call_id`，记录 `turn_id`、工具名、安全参数摘要、状态和耗时。
3. 从 LangGraph 流事件捕获真实工具生命周期，而不是根据文本推断。
4. 工具结果区分“技术成功”和“业务未找到”，避免成功率失真。
5. 为 `policy_search` 输出结构化 citation：政策编号、标题、类别、摘要和检索分数。
6. 增加 RAG 拒答阈值，并用小型问题集校准距离含义和阈值。
7. 为 Chroma 文档设置稳定 ID，记录政策文件哈希和 embedding 版本。
8. 只有政策内容或 embedding 配置变化时才重建索引。
9. 前端暂存工具轨迹与 citation，为工作台阶段提供数据源。

### 预计涉及文件

- 修改 `agent/events.py`、`agent/llm_agent.py`、`agent/session.py`。
- 修改 `agent/tools/policy_search.py`。
- 修改 `agent/rag/knowledge_base.py`。
- 修改 `ui/src/composables/useVoiceAgent.js`。
- 新增 `tests/test_tool_events.py`、`tests/test_policy_search.py`、`tests/test_knowledge_base.py`。
- 建议新增 `tests/fixtures/rag_cases.json`。

### 前后端协作

- 工具事件统一使用 `session_id + turn_id + call_id` 关联。
- 事件参数必须过滤手机号、地址、API Key 等敏感内容。
- `rag.citations` 或 `agent.finished.citations` 作为引用事实源；前端不再用正则作为主路径。

### 验收标准

- 一次订单查询能产生顺序正确的 called/finished 事件和耗时。
- 工具异常产生 failed 事件，但不会导致 WebSocket 崩溃。
- 政策回答即使不含固定句式，前端仍能获得真实 citation。
- 无关问题不会固定返回三条政策，也不会展示虚假引用。
- 政策未变化时重启不会重复写入相同向量文档。

### 测试计划

- 工具事件顺序、并行调用、失败和取消测试。
- RAG 命中、边界、无关问题和空知识库测试。
- 索引哈希、稳定 ID 和更新重建测试。
- 前后端事件契约 fixture 测试。

### 难点和风险

- LangGraph 的流事件格式与当前版本绑定，需要封装适配层。
- Chroma 返回值可能是距离而非相似度，阈值必须以实测结果为准。
- 工具参数和结果不能原样写日志或发送 UI，需要明确脱敏策略。

### 预计工时

**2-3 天。** 最大不确定性是 LangGraph 事件流和 Chroma 分数语义。

### 阶段交付物

- 前后端统一工具事件协议。
- 可验证的政策引用链路。
- 有版本控制和拒答能力的本地知识库。

## 7. Phase 4：客服工作台

### 阶段目标

将当前展示型语音页面改造成可用于演示实际客服工作流的三栏工作台。

### 当前状态

**未完成。** 当前只有对话、状态和语音控制，没有客户面板和工具调用轨迹。

### 开发任务与顺序

1. 扩展 `useVoiceAgent`，按会话保存当前客户、订单、工单、工具轨迹和 citation。
2. 新增 `CustomerPanel.vue`：脱敏客户资料、关联订单、历史工单。
3. 新增 `ToolCallLog.vue`：工具名、状态、参数摘要、耗时和错误信息。
4. 改造 `ConversationPanel.vue`：使用结构化 citation，显示工具关联状态。
5. 将 `App.vue` 改造成三栏布局：客户上下文、对话主区、工具轨迹。
6. 为窄屏设计标签页或抽屉式降级，避免三栏挤压。
7. 增加空状态、加载态、失败态和断线态。

### 预计涉及文件

- 修改 `ui/src/App.vue`。
- 修改 `ui/src/composables/useVoiceAgent.js`。
- 修改 `ui/src/components/ConversationPanel.vue`。
- 修改 `ui/src/styles/main.css`。
- 新增 `ui/src/components/CustomerPanel.vue`。
- 新增 `ui/src/components/ToolCallLog.vue`。
- 新增相应前端测试文件。

### 前后端协作

- 完全消费 Phase 3 的结构化事件，不在 UI 内重新解析业务文本。
- 客户面板只展示真实工具返回的数据；切换会话或断开时清理上下文。
- 工具失败不能覆盖对话区已有内容，应独立展示状态。

### 验收标准

- 查询客户后左栏展示脱敏资料、订单和工单。
- 中间栏持续显示 ASR partial、用户消息、Agent 流式回答和政策引用。
- 右栏实时显示工具执行中、成功、失败和耗时。
- 打断后旧轮工具/音频状态不会覆盖当前轮。
- 桌面和常见笔记本分辨率下无重叠；窄屏可完成同样操作。

### 测试计划

- 事件 reducer 单元测试。
- 客户面板、工具日志、引用组件测试。
- 使用固定事件序列进行前端集成测试。
- Chrome/Edge 手动检查麦克风授权、播放和响应式布局。

### 难点和风险

- 工具返回必须同时适合 Agent 与 UI，不能继续只返回难解析的纯文本。
- 工具事件较多时需限制历史数量，避免长会话页面性能下降。

### 预计工时

**2-3 天。** 最大不确定性是现有样式改造成三栏后的响应式适配。

### 阶段交付物

- 可演示的三栏客服工作台。
- 客户、对话、工具和引用的完整联动。
- 关键视图截图和演示录屏素材。

## 8. Phase 5：指标评估、测试固化与简历交付

### 阶段目标

形成可复现、可量化、能支撑简历表述和面试回答的工程证据。

### 当前状态

**未完成。** 现有错误日志不能证明性能指标，自动化测试仅覆盖少量工具。

### 开发任务与顺序

1. 定义时间点：音频开始、ASR final、Agent 开始、LLM 首 Token、TTS 首包、播放完成。
2. 每轮输出结构化 JSONL 日志，包含会话、轮次、状态、工具、引用、延迟和结果。
3. 统计工具技术成功率、业务命中率、RAG 接受率、取消率和各阶段延迟分位数。
4. 编写指标导出脚本，输出样本数、P50、P95、失败数和测试环境。
5. 固定前端依赖版本，检查 Python 版本与依赖兼容性。
6. 建立单元、Session 集成、WebSocket 契约和前端构建测试矩阵。
7. 准备 5 个固定面试演示场景和常见故障降级场景。
8. 只有真实测量后，才更新 README 和简历中的数字。

### 预计涉及文件

- 新增 `agent/metrics.py`、`agent/structured_logging.py`。
- 新增 `scripts/export_metrics.py`。
- 修改 `agent/session.py`、`agent/llm_agent.py` 和工具/RAG 模块。
- 修改 `requirements.txt`、`ui/package.json`、`ui/yarn.lock`。
- 扩充 `tests/`，新增前端测试配置。
- 最后修改 `README.md` 和 `PROJECT.md`，使状态与证据一致。

### 前后端协作

- 指标事件可以只写后端日志；开发模式下可选发送 `metrics.turn`。
- 不把 API Key、完整手机号、地址、原始音频写入指标日志。
- 统一前后端事件 fixture，防止协议字段漂移。

### 验收标准

- 至少完成 30 轮固定场景测试，并能导出样本数、P50/P95 延迟。
- 能区分成功、失败、取消和业务未命中，统计口径可解释。
- 默认测试不调用外部收费 API；外部服务冒烟测试显式开启。
- 新环境可以按 README 完成安装、启动和演示。
- 简历中的每个数字都能指向测试条件和导出结果。

### 测试计划

- 使用可控时钟测试指标计算。
- 测试日志脱敏和异常情况下的字段完整性。
- 运行全部后端单元与集成测试、前端测试和构建。

### 难点和风险

- 外部模型网络波动会影响延迟，报告必须注明网络、样本量和模型配置。
- 没有人工标注集时，不应宣称 ASR 准确率或 RAG 准确率。
- `latest` 前端依赖会降低可复现性，应在最终阶段固定版本并保留锁文件。

### 预计工时

**2-3 天。** 若需要建立人工 RAG 评测集，再增加 1 天。

## 9. 阶段里程碑与停止条件

| 阶段 | 核心交付 | 进入下一阶段的条件 |
|---|---|---|
| Phase 1 | 稳定的轮次、打断和断线处理 | 工具调用中打断不再破坏后续对话 |
| Phase 2 | 工单创建、查询、催办、历史 | 写操作具备业务校验和幂等保护 |
| Phase 3 | 工具事件与可信引用 | 前端不依赖解析模型文本获取事实 |
| Phase 4 | 三栏客服工作台 | 主演示场景可在一个页面完整呈现 |
| Phase 5 | 指标、测试和简历材料 | 所有简历陈述均有源码或数据证据 |

任何阶段未达到停止条件时，不提前进入依赖它的 UI 或指标开发。

## 10. 面试展示主线

建议将最终项目讲解控制在以下逻辑内：

1. 为什么选择 STT -> Agent -> TTS，而不是端到端 Speech-to-Speech。
2. 如何用 Session 状态机和 `turn_id` 解决流式并发、用户打断和迟到事件。
3. 如何处理 Agent 工具调用中的副作用、幂等和多轮上下文一致性。
4. 如何让 RAG 引用来自真实检索结果，而不是让模型自行生成标签。
5. 如何通过结构化工具事件驱动客服工作台，而不是解析自然语言。
6. 如何定义并测量首 Token、TTS 首包和端到端延迟。
7. 为什么当前继续使用 JSON Mock，以及它的并发边界和未来替换方式。
